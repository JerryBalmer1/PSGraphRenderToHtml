# v0.1.1 — `-ColorBy` was validated against a list the renderer does not have

2026-09-02. A patch release, and it corrects one parameter. The parameter is
worth a release because of what it was wrong about.

## What was wrong

`New-GraphRenderOptions -ColorBy` validated against `structure`, `scope`,
`type`. PSGraphRender v0.13.0's cytoscape settings schema accepts `structure`,
`dependents`, `blastRadius`, `dependencies`, `reach`. **The two sets share
exactly one member**, and the consequence ran in both directions:

- `scope` and `type` bound here and were rejected there. The renderer warned —
  `Setting 'ColorBy': 'type' is not one of: … Using structure.` — and drew
  `structure`. A caller who asked for one thing got another, and the only
  notice was a warning on a stream nobody was capturing.
- `dependents`, `blastRadius`, `dependencies` and `reach` could not be asked
  for at all. The renderer has drawn a heat ramp over each of them since the
  metrics existed; this module refused them at the parameter.

So the module's own docstring — *"every layout name and every interaction
default here was READ from PSGraphRender v0.13.0's cytoscape template set
rather than guessed"* — was true of the layouts and the knobs and not of this.
`ColorBy` either was never read, or the two drifted afterwards, and **nothing
in either repository would have noticed either way.**

## What changed

`-ColorBy` now accepts exactly the renderer's set, and refuses anything else
with a message that names the renderer, the accepted values, and what the two
retired values used to do. A `ValidateSet` could not carry that message, so the
validation is a `ValidateScript` with an `ErrorMessage` and an
`[ArgumentCompleter]` beside it, which keeps tab completion.

There is no deprecation window for `scope` and `type`. A deprecation window is
for something that used to work.

## The general defect, which is the reason this is worth writing down

**A `ValidateSet` is a promise about what the CALLEE will accept.** When the
callee is a different repository at a different version, the promise is a copy
of somebody else's list with no mechanism keeping it honest. Nothing fails; the
value is taken, and the behaviour quietly is not the requested one.

`tests/Options.Tests.ps1` now reads
`TemplateSets/cytoscape/Config/settings.schema.psd1` out of the resolved
PSGraphRender and asserts that every value it declares is accepted here. It is
the one check that would have caught this, and it goes red on the next drift in
either direction rather than on the next time somebody renders and squints.

Two literal copies of the set still exist, in the validator and in the
completer. A test compares them by behaviour rather than by text, because two
lists in one file that nobody diffs is the same defect at a smaller scale.

## Falsification

Run from the consuming harness, against a real render, three ways:

1. `-ColorBy blastRadius` binds and renders with **zero** renderer warnings,
   and the value reaches the document. Under v0.1.0 it could not be passed.
2. `-ColorBy scope` and `-ColorBy type` refuse before a render happens, naming
   both sides. Forced past the validator — reconstructing exactly what v0.1.0
   built — the renderer warns and downgrades, which is the defect, shown.
3. `-ColorBy structure` renders a document **byte-identical** to the one
   `origin/main` produces from the same graph, apart from the `generatedAt`
   stamp. The one shared member did not move.

The record is `plans/0041-operator-ux/colorby-falsification.txt` in
AI.Agent.Claude.PowerShellModuleBuilder, and the script beside it re-derives it
from a fresh clone.

## What did not change

The contract is untouched: `contract/producer-graph.schema.json` is still
`0.1.0` and is versioned independently of the module, as its own protocol says.
No producer's graph needs a line changed. The view model, the battery and the
overlay writer are the same.

## Node fills, and a thing not to re-attempt

The falsification does not read node colours out of the rendered HTML, because
they are not in it: cytoscape computes each fill in the browser from `ColorBy`
plus the theme and draws it into a canvas. Reading fills would mean
re-implementing the renderer's `fillFor` in the checker — a second copy of
another repository's rule, drifting unobserved, which is the defect this
release is about. The renderer's own acceptance is the observable, and it is
the right one: the fill followed the setting all along. The setting was what
never arrived.
